# 日常維護及驗收手冊

## 日常開發流程

每次修改前先建立分支或 checkpoint，修改後依次執行型別檢查、測試及建置。前端表單修改至少要測試空白欄位、數字欄位、動態新增列、刪除列、頁面重新載入及手機版寬度。

```bash
pnpm check
pnpm test
pnpm build
```

如果修改涉及資料庫 schema，先更新 `drizzle/schema.ts`，產生並審閱 migration，再在測試資料庫驗證。不得以直接刪除資料表的方式處理 migration 問題。

## 學校端驗收

建立測試學校帳戶後，確認可以登入 Portal，進入 E、S、G 頁面，填寫基本資料和章節資料，保存草稿，再返回 Portal 確認草稿狀態。補齊資料後正式提交，確認學校端不能再修改正式提交資料。

## 管理端驗收

使用獨立管理員帳戶進入管理頁面，確認能查看學校提交、看到報告年度及各章資料，能標記審閱、輸入回覆摘要，以及上載和下載報告檔案。確認一般學校帳戶不能讀取其他學校資料或管理員功能。

## 事故處理優先順序

若網站無法啟動，先查看部署及 runtime logs，再執行 `pnpm check` 和 `pnpm build`。若是依賴遺失，重新執行 `pnpm install`；若是環境設定問題，確認變數名稱存在但不要把 Secret 寫入 log。若是最近的程式碼修改造成故障，使用版本控制或平台 checkpoint 回到最後一個已驗證版本，不要使用不可逆的 `git reset --hard` 取代有記錄的回滾程序。

若懷疑帳戶或憑證外洩，先撤銷相關 session 和 API key，輪換 `JWT_SECRET` 及資料庫密碼，再檢查登入及存取記錄。若資料可能被錯誤刪除，立即停止破壞性操作並保存現有資料庫狀態，交由資料擁有者決定還原方案。

## 版本基準

本次交接以 checkpoint `7ccfe25b` 為基準。該版本已完成 E、S、G 頁面輸入流程驗證，並通過 TypeScript 檢查、15 項 Vitest 測試及正式建置。後續維護者應先以此版本建立 staging，再將新修改分批合併。

## 最低交接驗收

交接不應以「已收到 ZIP」作為完成。只有在新維護者可以不使用原持有人的 Manus 帳戶，獨立完成安裝、啟動、登入、草稿保存、正式提交、管理員回覆、報告檔案操作和部署後回滾，並完成憑證輪換後，才算完成技術交接。
